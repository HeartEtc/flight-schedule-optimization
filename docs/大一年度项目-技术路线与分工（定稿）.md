## 0. 一句话技术路线

```
导师原始数据
   │  ① Python（pandas）清洗 + 特征工程            → B
   ▼
flight_features.csv（唯一可信数据源）
   │  ② MySQL / SQL 统计 + 判断高峰时段 + 统计基线    → B
   ▼
peak_hours.csv / *_stats.csv / baseline_metrics.csv
   │  ③ Java + Weka 延误预测                        → A
   ▼
flight_predictions.csv（延误概率）+ metrics.json
   │  ④ Java 调整规则生成 + 前后对比                → A

   │  ⑤ R 制图制表 + 统计检验                       → D
```

**一句话**：`Python 洗数 → SQL 判高峰 → Java 预测延误 → Java 出调整与对比 → R 出图 → 文书核对成稿`。

## 1. 关键口径（四条铁律，答辩命门）

### 铁律 1｜"判断高峰"与"预测延误"必须物理隔离

| 概念 | 性质 | 谁做 | 用途 |
|---|---|---|---|
| **判断高峰** | 描述统计（看整体） | B / SQL | ① 报告结论；② 调整规则的**筛选条件** |
| **预测延误** | 预测（猜个体） | A / Java | 挑出高风险航班 |

**铁律原文**：

> 高峰时段**只用于"筛选哪些航班要调整"，不得作为延误预测模型的输入特征**。

唯一例外：若高峰**改用"计划航班量"定义**（前 25% 的小时，不含延误结果），才允许作为模型特征。

**原因**：延误预测要猜"会不会延误"，而高峰如果是"由延误结果算出来的"，把它当特征喂回去，模型等于用答案的一部分猜答案（目标泄露）。答辩第一问就会戳穿。

### 铁律 2｜延误口径全组唯一

- 延误 = `dep_delay_minutes > 15`（《航班正常管理规定》15 分钟口径）
- 这个阈值只在**入库时算一次**，写进 `is_delayed` 字段，全组引用，禁止各处各算。

### 铁律 3｜统计量只算一次

按小时/按航线的分组统计**只在 B 的 SQL 里算一次**，导出 CSV。A 和 D 只消费 CSV，**不重算**——否则报告里会出现多个不同数字，答辩崩。

### 铁律 4｜格式与数据纪律

- CSV：**UTF-8 无 BOM**，列名小写 + 下划线，缺值用空字段
- 原始数据**不进 Git**；聚合结果 CSV **进 Git**（保证图可复现）
- 交接物永远是文件，不用口述/截图传数据

## 2. 四人分工（定稿）

| 人 | 工具 | 负责环节 | 交付物 |
|---|---|---|---|
| **B** | Python + MySQL | ① 清洗 + 特征工程；② 入库 + 高峰识别 + 统计基线 | `flight_features.csv`、`hourly_stats.csv`、`route_stats.csv`、`peak_hours.csv`、`baseline_metrics.csv`、`data_quality.csv` |
| **A（本人）** | Java + Weka | ③ 延误预测；④ 调整规则 + 前后对比 | `flight_predictions.csv`、`metrics.json`、`adjustments.csv`、`comparison.csv` |
| **D** | R | ⑤ 制图制表 + 统计检验 | `figures/*.png`、`tables/*.csv`、检验结论 |
| **C** | Excel / Word | 字段说明、数据核对、报告主笔、PPT | `字段说明.md`、核对记录、`报告.docx`、PPT |

> **现状更正（10-15）**：立项阶段 C 的文书工作**由 A（队长）统筹、队员协助完成**，不设专职 C。A 在立项阶段是"队长 + 报告统筹 + 方法可行性主笔"三重角色。

### 环节职责细节

**B｜Python + SQL**
- 清洗：丢缺失、类型转换、时间统一、去重，输出 `flight_features.csv` + 清洗日志（丢了多少、按什么规则）
- 高峰识别（描述统计）：按"计划起飞小时"分组，产出 `peak_hours.csv`
- 统计基线：全样本延误均值/延误率，作为 ML 结果的对照

**A｜Java + Weka**
- ARFF 转换：`flight_features.csv` → `flight_train.arff`
- 延误预测：单模型起步（见第 3 节降级），10 折交叉验证，输出概率 + 指标
- 调整规则：`高峰时段 ∩ 高延误风险` → 调 ±10~15 分钟
- 前后对比：原始 vs 调整后的延误指标

**D｜R**
- 高峰图、延误分布、Top 航线、**调整前后对比图**、模型 vs 基线对比图
- 统计检验：调整前后延误差异是否显著

**C｜文书 + 核对**
- **第 1 周先出字段说明表**（A/B 清洗和建模都依赖它）
- 抽样核对：抽 20 行手工验证 B 的清洗结果；用 Excel 验算一个小时的均值对 B 的 SQL 结果
- 报告主笔、PPT、排练

## 3. 交付分期（立项阶段 vs 项目阶段）

**立项阶段（2026-11 前）不交代码，交的是"方法可行性 + 计划"。** 代码与模型是立项通过后、约一年周期内的事。

| 阶段 | 交付物 | 时间 |
|---|---|---|
| **立项阶段** | 《立项报告》：背景、研究内容、**方法可行性**、进度安排、分工、参考文献 | 2026-11 答辩 |
| **项目阶段（一年）** | 先单模型跑通全链路 → 再上 Stacking；逐步补校准、敏感性分析 | 立项通过 ~ 2027-10 |

**渐进顺序（项目阶段内部）**：

| 里程碑 | 内容 | 目的 |
|---|---|---|
| M1 | B 清洗 + 高峰 + 基线；A 单模型（J48 或 Logistic）+ 与基线对比 | 先证明"整条链能跑通、模型比基线好" |
| M2 | A 上 Stacking（4 基模型 + Logistic） | 提升指标、支撑"集成增益" |
| M3 | 调整规则 + 前后对比 + 校准/敏感性 | 核心交付 + 答辩弹药 |

**理由**：先单模型后 Stacking 是工程上正确的渐进方式——**每一步都可验证、可答辩**，而不是把风险压在最后一个月一次性交付。

## 4. 依赖与关键路径

```
导师数据 → B(特征+高峰+基线) → A(预测) → A(调整+对比) → D(图) → C(报告)
```

| 依赖 | 卡住的后果 |
|---|---|
| 导师数据不到位 | 全组停摆 → **B 先用 20 行样例开路** |
| B 的 `flight_features.csv` 不出 | A 无法做 ARFF、D 无图可画 |
| B 的 `peak_hours.csv` 不出 | A 的调整规则没有筛选条件 |
| A 的 `comparison.csv` 不出 | D 画不了对比图、C 写不了结论 |

**关键路径：B → A → D → C。B 是第一个瓶颈，A 是技术难度最高的单点。**

## 7. 分工合理性评估结论（摘要）

**结论：一年周期下，分工合理；四周的真正压力在《立项报告》本身，不在代码。**

| 风险 | 说明 | 对策 |
|---|---|---|
| **A 的 Java→ML 差距** | 唯一的 Java 人要做 Weka 建模，但**有一整年学习窗口**，立项阶段只需写清"方法可行性" | 项目阶段按 M1 单模型 → M2 Stacking 渐进；立项前 A 吃透方法论即可 |
| **B 前期负载最重** | 清洗+特征+高峰+基线全在 B，且是全链第一瓶颈 | 项目阶段 B 先交最小闭环样例，解锁 A/D/C |
| **C 定位模糊 + 后期全压** | 零基础做"数据核对"有门槛，报告集中在立项阶段爆发 | C 第 1 周先出字段说明表 + 报告框架；核对由 B 带 |
| **串行依赖 + 单点** | 每环节一个人，任一掉链子整链断 | 每周 15 分钟同步 + 交付物可复现，盯住 B→A→D→C |

> 详细评估见正文对话。
