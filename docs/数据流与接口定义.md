# 四人分工：数据流与接口定义（Weka Stacking 版）

> 制定：2026-10-13｜依据：已敲定内容汇总（第 11 号项目）
> 用途：动手前把"谁加工什么、输入输出是什么格式"定死。**接口一旦定了，四个人可以并行开工。**

---

## 一、整体数据流（一张图看懂）

```
Kaggle 原始 CSV（raw）
        │
        │  ① Java：读入 + 清洗（丢缺失、时间格式统一、去重）
        ▼
flights_clean.csv          ← 全组唯一可信数据源（单一事实来源）
        │
        ├──② B：导入 MySQL → SQL 统计 → hourly_stats.csv / route_stats.csv
        │        （用途：高峰时段识别 + 数据完整性校验 + 统计基线）
        │
        ├──③ Java：特征工程 → flight_train.arff（Weka 可读）
        │
        ├──④ Java + Weka：Stacking 训练与评估 → 指标 + 预测结果
        │        flight_predictions.csv（每条航班的延误概率）
        │
        ├──⑤ Java：调整规则生成 → adjustments.csv
        │        + 调整前后对比指标 comparison.csv
        │
        └──⑥ D：R 读上述 CSV → figures/*.png + 统计检验结论
                 C：核对 + 报告 + PPT
```

**核心原则**：`flights_clean.csv` 是**唯一可信数据源**。**清洗只做一次**（A 做），B、D、C 都只消费它或它的下游产物——**绝不各自重新清洗**。

## 二、逐个环节：谁做、输入什么、输出什么

### 环节 ① 原始数据 → 清洗后数据

| 项 | 内容 |
|---|---|
| **谁做** | **A（Java）** |
| **输入** | Kaggle 原始 CSV（`data/raw/*.csv`） |
| **输出** | **`data/output/flights_clean.csv`** |
| 输出列 | `date, flight_no, airline, origin, dest, sched_dep_time, dep_delay_minutes, ...`（**列名定死后不许改**） |
| 编码 | **UTF-8 无 BOM** |
| 关键规则 | 丢弃关键字段缺失的行；时间统一为 `yyyy-MM-dd HH:mm`；延误分钟转 `int`；去重 |
| 交付附带 | **清洗日志**：原始 N 行 → 保留 M 行，丢弃按原因分类统计 |
| 支持报告哪一节 | 研究内容第 1 条（数据清洗）、方法可行性说明 |

**Java 用到**：IO（`BufferedReader`）、`String.split`、`LocalDate`/`LocalDateTime`、`ArrayList`、异常处理 —— **全部是 A 已学或本周要学的内容**。

---

### 环节 ② 清洗数据 → 数据库统计（供高峰识别与校验）

| 项 | 内容 |
|---|---|
| **谁做** | **B（Python + MySQL）** |
| **输入** | `flights_clean.csv` |
| **输出 1** | `data/output/hourly_stats.csv`：`hour, flight_count, avg_delay, delay_rate` |
| **输出 2** | `data/output/route_stats.csv`：`route, flight_count, avg_delay, delay_rate` |
| **输出 3** | `data/output/peak_hours.csv`：`hour, flight_count`（**高峰时段识别结果**） |
| 关键定义 | 延误 := `dep_delay_minutes > 15`（**与《航班正常管理规定》的 15 分钟口径一致**） |
| 交付附带 | 建表脚本 `schema.sql`、导入脚本 `import_to_mysql.py`、环境说明 |
| 支持报告哪一节 | 研究内容第 2 条（高峰时段识别，**统计方法，不占基模型层**）、方法可行性 |

**核心 SQL**：
```sql
SELECT HOUR(sched_dep_time) AS hour,
       COUNT(*) AS flight_count,
       ROUND(AVG(dep_delay_minutes), 1) AS avg_delay,
       ROUND(SUM(CASE WHEN dep_delay_minutes > 15 THEN 1 ELSE 0 END) / COUNT(*), 3) AS delay_rate
FROM flights
GROUP BY hour
ORDER BY hour;
```

> **高峰时段定义要写进报告**，例如："航班量排名前 25% 的小时，或延误率高于全样本均值 1.5 倍的小时"。**必须给出明确标准**，否则答辩会被追问。

---

### 环节 ③ 清洗数据 → 特征工程 → ARFF

| 项 | 内容 |
|---|---|
| **谁做** | **A（Java）** |
| **输入** | `flights_clean.csv` + 气象数据 CSV（若需要） |
| **输出** | **`data/output/flight_train.arff`**（Weka 唯一认的格式） |
| 特征清单 | ① 数值：`hour`、`day_of_week`、`month`、`is_peak_hour`、气象数值 |
| | ② 名义：`airline`、`origin`、`dest`、`weather_condition` |
| | ③ **类别标签**：`delayed`（`dep_delay_minutes > 15` → yes/no） |
| 关键约定 | **与 B 的 `peak_hours.csv` 保持一致**——`is_peak_hour` 的判定必须用 B 输出的高峰时段，不能自己另定一套 |
| 支持报告哪一节 | 研究内容第 3 条（特征工程） |

**这是你的核心工作**：ARFF 格式写错了 Weka 直接读不进去，而**格式规范（`@relation` / `@attribute` / `@data` 三段）必须严格**。

---

### 环节 ④ Stacking 模型训练与评估

| 项 | 内容 |
|---|---|
| **谁做** | **A（Java + Weka）** |
| **输入** | `flight_train.arff` |
| **输出 1** | **评估指标**：准确率 / 精确率 / 召回率 / F1 / AUC（写入 `metrics.txt` 或 CSV） |
| **输出 2** | **`data/output/flight_predictions.csv`**：`flight_no, date, sched_dep_time, delay_probability` |
| 模型配置 | 一层：J48、RandomForest、SMO（**必须开 `-M`**）、NaiveBayes；二层：Logistic |
| 评估方式 | 10 折交叉验证（Weka 默认），或留出法 |
| 支持报告哪一节 | 研究内容第 4 条、方法可行性（引用 Wolpert 1992） |

**必须记录到报告里的技术细节**（你已核实过，直接引用）：
- SMO 必须开启 `-M`（`buildCalibrationModels`），否则只输出硬 0/1，**Stacking 拿不到有效概率**
- Weka 的 SMO 内部已自动归一化、自动处理名义属性与缺失值，**无需再加 `Normalize` 过滤器**
- SMO 的系数基于归一化后的数据，**不能用于解释特征重要性**

### 环节 ⑤ 调整规则生成与前后对比（核心交付）

| 项 | 内容 |
|---|---|
| **谁做** | **A（Java）**，B 提供高峰时段与统计口径 |
| **输入** | `flight_predictions.csv` + `peak_hours.csv` |
| **输出 1** | **`data/output/adjustments.csv`**：`flight_no, date, original_time, adjusted_time, delta_minutes, reason` |
| **输出 2** | **`data/output/comparison.csv`**：`scenario(original/adjusted), avg_delay, delay_rate, delayed_count` |
| 规则约束 | ① **只调整高峰时段内的航班**；② **每时段调整数量设上限**（立项表要求"少量航班"）；③ 优先调延误风险高、且推后不挤占后续时刻的航班；④ 调整幅度 **±10—15 分钟** |
| 支持报告哪一节 | 研究内容第 5、7 条（核心交付 + 效果验证） |

> **注意"两层定位"的边界**（已敲定）：**旅客提醒 / 改签引导 / 登机口建议属于配套层，不得纳入"优化效果验证"**——因为它们不改变时刻表，无法证明降低延误率。**报告里必须写清这条边界**，否则逻辑会被质疑。

## 四、依赖关系与关键路径

| 依赖 | 时机 | 卡住的后果 |
|---|---|---|
| Kaggle 数据集选定 → A | **第一优先** | 全组停摆（决定字段映射与案例机场） |
| **A 先造 20 行样例 CSV** | 第 1 周 | B、D、C 全部干等 → **所以样例数据是启动键** |
| A → `flights_clean.csv` | 第 2 周 | B 无数据可入库、A 自己也无法做特征工程 |
| B → `peak_hours.csv` | 第 2 周末 | **A 的 `is_peak_hour` 特征做不出来** |
| A → `comparison.csv` | 第 4 周 | D 画不出对比图、C 无法写结论 |

**关键路径：A → B（高峰时段）→ A（特征）→ A（模型）→ A（对比）→ D/C**

**结论：A 是瓶颈**。所以：
- **A 的样例数据要最早产出**（解锁所有人）
- **B 的高峰时段识别要尽早**（它是 A 特征工程的前置）
- **A 的时间投入要盯住 4 小时/周**，超了就跟老师说

## 五、MySQL 在这个项目里的真实定位

理论上 Weka 训练不需要数据库。但 B 的 MySQL 有**三个真实用途**，写进报告不牵强：

| 用途 | 说明 |
|---|---|
| **数据完整性校验** | `SELECT COUNT(*)` 与原始行数、清洗后行数对账；`NULL` 检查；主键去重 |
| **高峰时段识别** | `GROUP BY hour` 是最自然的实现，且结果可复现 |
| **统计基线对照** | 机器学习模型的输出要和"纯统计基线"对比——**否则无法说明模型有没有带来增益** |

**第三点尤其重要**：报告里可以写"**与单纯按历史平均延误的基线相比，Stacking 模型的 F1 提升了 X**"。**没有基线对照的机器学习结果，答辩是站不住的。**
