# 技术方案：Python+SQL 洗数 → Java 建模 → R 出图表

> 制定：2026-10-13｜用途：确认新的技术分工方案是否可行，以及各环节的输入输出

---

## 一、结论：可行，而且和主流数据团队的工种划分一致

```
Kaggle 原始 CSV
      │
      ▼  ① Python（pandas）：清洗 + 特征工程
data/features/flight_features.csv
      │
      ├──▶ ② MySQL：入库 + 数据质量体检 + 高峰识别 + 统计基线
      │        └─▶ *.csv（统计结果）
      │
      ▼  ③ Java：CSV → ARFF + Weka Stacking 训练
data/model/flight_predictions.csv（延误概率）+ metrics.json
      │
      ▼  ④ Java：调整规则 + 前后对比
adjustments.csv + comparison.csv
      │
      ▼  ⑤ R：制图制表
figures/*.png + tables/*.csv + 统计检验结论
```

**分工与真实数据团队一致**：

| 环节 | 工具 | 类比真实岗位 |
|---|---|---|
| 清洗与特征 | **Python（pandas）** | 数据分析师 / 数据开发 |
| 存储与聚合统计 | **SQL** | 数仓开发 |
| 建模 | **Java + Weka** | 算法工程（本项目的教学载体） |
| 制图与检验 | **R** | 数据分析 / 可视化 |

**这个组合写进报告是站得住的**——它是"多工具协作的数据分析流水线"，说得出每一段为什么用这个工具。

**为什么 Java 只做这一层也够**：

3. 训练/评估/调参/对比基模型的工作量不小，**并不比清洗轻松**

## 三、这个方案的三个风险（必须处理）

### 风险 1：**`is_peak_hour` 的口径必须唯一** ★最要紧

`is_peak_hour` 既是**SQL 的统计结论**，又是**模型的输入特征**。**如果 Python 自己按另一套标准算了一遍，模型的输入和报告的结论就对不上**。

**对策**：
- 高峰时段**只在 MySQL 里算一次**
- Python **从 `peak_hours.csv` 读进来 join**，不自己算
- **交付后 A 打印前 5 行贴群里确认**

### 风险 2：Python 和 R 重复做"统计"

Python 很自然会顺手 `groupby` 算个平均延误，R 也可能自己再算一遍 → **报告里出现两个不同的数字**。

**对策**：
- **统计量只在 SQL 里算一次**（这是全组铁律）
- **Python 只做"逐行级的清洗与特征"，不做"分组统计"**
- **R 只画图和做检验，不重算分组统计量**

### 风险 3：A 的 Java 练习量下降

清洗挪到 Python 之后，你在 Java 侧只剩 ARFF 转换 + 模型 + 规则。

**对策**：**Weka 那层的工作量足够**（ARFF 格式规范、4 个基模型配置、SMO 的 `-M`、交叉验证、结果对比、模型保存），并不比清洗轻松。

**不建议把清洗挪回 Java**：pandas 在缺失值处理与多表关联上确实更高效，而 Java 侧应该集中做"别人替不了的环节"——Weka 只能由 Java 调用。

## 五、报告里怎么表述这个技术栈（避免显得"堆工具"）

**别写成"我们用了 Python、MySQL、Java、Weka、R 五种技术"**——那听起来像凑数。**要写成"一条流水线，每段用最合适的手段"**：

> 本项目采用多工具协作的流水线实现：**数据清洗与特征工程**使用 Python（pandas）完成，因其在缺失值处理与多表关联上效率更高；**数据存储与分组统计**使用 MySQL，通过 SQL 以可复现的方式完成高峰时段识别、数据质量核验与统计基线计算；**延误预测**使用 Java 调用 Weka 实现两层栈式集成（Stacking）模型；**结果可视化与统计检验**使用 R（ggplot2）完成。各环节以 CSV 作为标准化接口，保证每一段可独立复现与验证。

**这段话的价值**：
- 每段都给了"为什么用这个工具"
- "CSV 作为标准化接口"说明你们考虑了协作
- 直接回应导师"方法可行性说明"的要求

## 六、待你确认的两件事

1. **气象数据是否独立 CSV、按什么键关联**（若按"机场 + 日期"，Python 的 `merge` 一步能合并；若需要按小时对齐，复杂度会上升）
2. **Python 侧是否负责用 `liac-arff` 直接生成 ARFF**——**我建议不**：
   - 依赖第三方库，版本兼容要和 Weka 对齐，**容易踩坑**
   - 由 Java 做转换，**ARFF 只有一处生成逻辑**，出问题好定位
   - 顺便让 A 保留一段真实的 Java 编码工作
